# AGENTS.md

## Project concept

spartan-torch — библиотека кастомных слоёв и вспомогательных заготовок для PyTorch.

**Цель:** быстро дообвешивать/адаптировать модели для файнтюна и собирать кастомные архитектуры из кирпичиков. Для трейн-лупа возможно подключение тяжёлых фреймворков (pytorch-lightning и пр.) — это отдельное решение, не фиксируем его здесь.

**Что входит в концепцию (стабильное ядро):**
- Кастомные слои и примитивы, которых нет в `torch.nn` (напр. `LayerNorm2d`, специфические активации)
- Строительные блоки для кастомных архитектур

**Что под вопросом (открытые решения):**
- Утилиты для трейн-лупа: метрики, callbacks, лёгкий тренер
- Утилиты для файнтюна: заморозка по паттернам, замена голов, hooks

  Актуальность обоих пунктов зависит от того, подключаем ли мы pytorch-lightning: если да — часть их дублируется и отпадает. Решаем по мере необходимости через правило оценки релевантности ниже.

**Решение по трейн-лупу в экспериментах (2026-08):** NLP-задачи идут на HF `transformers` (Trainer + PreTrainedModel, см. `experiments/llm/tinyllama/`), CV — на `pytorch-lightning` (см. `experiments/image_classification/`). Оба фреймворка — зависимости extra `experiments`; сама библиотека `spartan_torch` свободна от обоих.

**Что НЕ входит (важно):**
- Реимплементация стандартных моделей (ResNet, VGG, transformers) — их берём из `torchvision`/`huggingface` с предобученными весами
- Дублирование того, что уже есть в `torch.nn` без добавленной ценности

## Rule: evaluate relevance before work

Перед любой значимой работой (новый модуль, файл, фича) оцени её полезность относительно концепции проекта:

1. **Что решает** — какую боль закрывает?
2. **Кто использует** — реальный сценарий использования (пример кода)?
3. **Дубль?** — есть ли аналог в `torch.nn`/`torchvision`/стандартных экосистемах? Если да — что добавляет наш вариант?
4. **Вердикт** — входит в концепцию или нет.

Если работа не проходит п.3 или не имеет ясного сценария — предложить альтернативу или отклонить. Не писать код ради кода.

## Rule: ecosystem compatibility & current practices before implementation

Любая модель/слой/утилита должна вписываться в современную ML-экосистему. При обсуждении или проектировании реализации (до/вместе с кодом) дай актуальную справку по принятым практикам и совместимостям:

1. **Актуальность** — сверяй практики с текущими версиями фреймворков (Context7/веб-доки), не полагайся на память: API могло измениться.
2. **HF transformers** — что нужно для `PreTrainedModel`/`GenerationMixin` (конфиг, типинг весов, `Cache`/`DynamicCache`, `save_pretrained`/`from_pretrained`, `generate`).
3. **pytorch-lightning** — как ложится в `LightningModule`/Trainer (forward-контракт, `training_step`/`validation_step`, state_dict-совместимость чекпоинтов).
4. **Формат весов** — `safetensors`, tyings/типы тензоров, сериализация `state_dict`.
5. **Исполнение** — `torch.compile`/`torch.export`, SDPA, bf16/fp16/amp, device-агностичность (`meta`-device init для больших моделей).
6. **Вердикт** — что гарантируем как совместимое, где грань между «совместимо с X» и «не зависит от X» (библиотека `spartan_torch` остаётся свободной от тяжёлых фреймворков).

Цель: написанные модели переносятся в реальный пайплайн (HF Trainer, PL, экспорт) без переписывания.
